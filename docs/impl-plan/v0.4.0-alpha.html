baseline 3e7eae8 · written 2026-09-06

Browser clients, at parity with meme

TentaCron answers browsers since 0.2.0: an exact-origin allow-list under server.cors.allowed_origins, preflights for every method, a fixed set of exposed headers. The sibling service meme goes further, and a frontend that talks to both meets two policies with different edges. This release brings TentaCron's browser policy to meme's semantics where they apply, keeps what TentaCron already does better, and adds what a browser client of a job queue needs that a stateless simulation API never did: a readable Retry-After, a reload without restart, and a guide with a working page. Nothing here touches the job pipeline; every item is in the HTTP layer, its configuration, its tests or its documentation.

Rules that apply to every item

  • One item, one conventional commit, with its tests, its documentation and its CHANGELOG.md entry under Unreleased in the same commit. Subjects are given below; bodies explain the why, as the history does.
  • The gate runs before every commit and must fail hard: go build ./..., go vet ./..., go test -race -shuffle=on ./..., golangci-lint run, make lint-openapi, mkdocs build --strict; the phase tip also passes the stress gate, GOMAXPROCS=2 go test -race -shuffle=on -count=3 ./....
  • Tests before behaviour. Phase 0 records what the middleware does today; each later item flips exactly the cases it changes and names them in its text. A new parser of untrusted input, the origin matcher, gets a fuzz target, as the pull-request template requires.
  • Goldens change only for intended behaviour. One transcript is added; the header recording is opt-in per step, so no existing transcript moves. The regenerated file is read line by line before it is accepted.
  • Documentation is part of the item, not a phase after it. Reference pages, README, configuration examples and the OpenAPI description move in the commit that changes what they describe; phase 3 holds only the documents that are deliverables in their own right.
  • Work on a branch named after the phase (test/phase-0-cors-baseline, feat/phase-1-cors-parity, and so on), fast-forwarded onto main when the phase is green, as every earlier phase was.

OrderPhases and their dependencies

Phase 0 first, so that every later change is measured against a recorded baseline. Inside phase 1, the matcher (1.1) lands before the preflight semantics (1.2) that use it, and the header sets (1.3) before the knobs (1.4) that extend them. Phase 2 needs the policy object from 1.1 to swap it atomically. Phase 3 documents the finished behaviour, so it comes last; its example page is what the release checklist runs in a browser.

Match wildcard and subdomain origins

Problem

An allow-list of exact origins cannot express "every preview deployment of the frontend" (https://pr-123.app.example.org) or "any origin" for a public read-only deployment behind a key with the ceilings 0.3.0 added. 0.2.0 refused wildcards so a key stays confined to its frontend; the per-key max_queued, max_concurrent and max_priority ceilings now bound what a leaked key can do, and meme took the other decision. The apex must never match a subdomain pattern, and evil-example.org must never match *.example.org.

Change

allowed_origins accepts, as meme does, exact origins, the single entry *, subdomain wildcards scheme://*.host matching any depth below the host and never the host itself, and the literal null only when listed. Matching is case-insensitive over lower-cased entries. The policy is built once: an exact set, a wildcard list of prefix and suffix, an allow-all flag. Validation: * only on its own, a wildcard only as the first label, no path or trailing slash, no empty entry; tentacron validate prints a warning line when * is set, because a key in a page on any origin is a key on every origin.

Tests

The matrix cases wildcard origin, subdomain wildcard (depth two matches, apex and look-alike host do not), null origin, case-insensitive. FuzzOriginAllowed feeds random origins to a policy with a mixed list and checks the answer against a slow reference implementation; it must never panic and never allow what the reference refuses. Validation cases for each rejected shape.

Docs

Configuration row for allowed_origins rewritten with the three shapes and the warning; config.example.yaml comment. CHANGELOG under Added, with a Changed line that the 0.2.0 no-wildcard rule is lifted.

Answer every preflight itself, with the full Vary set

Problem

A preflight from an origin that is not allowed falls through to the mux, which answers 405 with an Allow header: the browser reports a method error instead of a blocked origin, and the method list is handed to a page that was refused. Preflights vary only on Origin; a cache that keys on the requested method or headers can serve one preflight's answer to another.

Change

The middleware answers every preflight (OPTIONS with Access-Control-Request-Method) before the mux and before authentication, as it already does for allowed origins: a denied origin gets 204 with Vary: Origin, Access-Control-Request-Method, Access-Control-Request-Headers and no Access-Control-* header, so the browser blocks the request on its own; an allowed origin gets the same Vary set plus the allow headers. Access-Control-Allow-Origin is the literal * only for allow-all without credentials, otherwise the echoed origin. An OPTIONS without the request-method header keeps its 405 and Allow, as in meme.

Tests

Flips the matrix cases preflight from a denied origin and Vary on a preflight; the browser-preflight golden moves for exactly those two steps, named in the commit body.

Docs

API reference, Browsers paragraph. CHANGELOG under Changed: a denied preflight answers 204 instead of 405.

Expose Retry-After and allow Authorization

Problem

0.3.0 added 429 queue_full with a Retry-After; the header is not on the CORS safelist and not in the exposed set, so a browser client sees the 429 and cannot read when to retry. meme allows Authorization on preflights for an authenticating proxy in front of the API; TentaCron's ADR-0008 puts such a proxy in scope and its preflight would fail today.

Change

The exposed set becomes X-Request-ID, Allow, Retry-After, Content-Disposition, Content-Length, Content-Range, Accept-Ranges; the allowed request headers become Content-Type, X-API-Key, Idempotency-Key, X-Request-ID, Range, Authorization. A test scans the package source like the literal-scan test from 0.3.0 does: every header name the handlers set with Header().Set is either CORS-safelisted or in the exposed set, and every header the handlers read is in the allowed set, so the next header added to a handler fails the build instead of silently being unreadable from a page.

Tests

The scan test; matrix case exposed headers extended. The 429 response in the OpenAPI description already declares Retry-After.

Docs

API reference, Browsers paragraph: the two sets, spelled out. CHANGELOG under Fixed.

The opt-in knobs: credentials, max-age, private network, extra headers

Problem

meme's CORSConfig offers credentials, a preflight max-age, Chrome's Private Network Access preflights and custom header lists; TentaCron hard-codes all four. A frontend behind a cookie-based SSO proxy needs credentials; a page on the public internet calling an instance on the institute's network needs the private-network answer; a proxy that adds its own header needs it allowed.

Change

Under server.cors, with meme's names in YAML form and the same semantics: allow_credentials (default off; the response then always echoes the specific origin, never *), max_age (duration, default 10 minutes, Chromium's cap; 0s omits the header), allow_private_network (default off; answers Access-Control-Request-Private-Network affirmatively when on), allowed_headers and expose_headers as additions to the built-in sets from 1.3, with the single entry "*" in allowed_headers meaning echo mode. No allowed_methods: the API's method set is known and complete. Validation per the Fetch specification, as meme's Validate: * origin with credentials refused, * in expose_headers with credentials refused, negative max_age refused. tentacron validate and the start-up log print one line: origins (and how many are wildcards), credentials, private network.

Tests

Matrix cases credentials (echoed origin, the Allow-Credentials header on preflight and response), max-age (default, custom, omitted), private network (only when asked and enabled), allowed headers wildcard (echo of the requested list), validation cases for each refused combination. The config tests cover defaults and the YAML shape.

Docs

Configuration table: one row per key. Both configuration examples. CHANGELOG under Added.

Apply CORS changes on SIGHUP

Problem

server.* is startup-only, so a new frontend origin means a restart, and a restart drains the queue and parks long-polls. The upstream response cap learned to swap on reload in 0.3.0; the CORS policy is the same shape of problem.

Change

The middleware holds the policy in an atomic.Pointer[corsPolicy]; the reload hook in main.go builds a new policy from the reloaded configuration and swaps it, as it calls SetMaxBody today. restartRequired compares server without its cors field, so a CORS-only change reports nothing to restart. A policy that is disabled at start can be enabled by reload and vice versa: the middleware is always installed and a nil-equivalent policy is the no-op.

Tests

The provider test: a CORS-only change is hot. The process lifecycle test from 0.3.0 gains a step: reload with a new origin, the next preflight from it answers 204 with the allow headers, without a restart. The stress gate on the phase tip, since the swap races requests.

Docs

Operations, Reloading configuration: server.cors moves to the hot list. CHANGELOG under Changed.

RisksEach risk, analysed

The wildcard origin weakens the key-in-a-page stance

Mechanism. 0.2.0 refused wildcards so that a key embedded in a page could only be used from that page's origin. With * allowed, a key read out of a page works from any page.

Likelihood and impact. Certain for a deployment that chooses *; the impact is bounded by what the key may do: its max_queued, max_concurrent and max_priority ceilings, its client scope for reads, and revocation per key.

Detection. tentacron validate and the start-up line warn on *; the request log names the origin.

Mitigation. The default stays off; exact origins and subdomain wildcards cover the real cases without *; the guide's security section and ADR-0009 state the trade-off in plain words and recommend a backend-for-frontend where the key must stay secret.

Residual. An operator who sets * for a key with the admin role exposes every client's requests to any page that learns the key. Named in the guide; not prevented, because the same operator can revoke the key.

A changed status for denied preflights

Mechanism. 1.2 turns the 405 a denied preflight gets today into a 204. A monitoring rule counting 405s, or a client that read the Allow header from a preflight, would see a change.

Likelihood and impact. Low: browsers never surfaced the 405 usefully, and no documented client reads Allow from OPTIONS; the non-preflight OPTIONS keeps its 405.

Detection. The phase 0 matrix and the golden record the old answer and move in 1.2 with the two steps named.

Mitigation. A Changed line in the CHANGELOG under a heading of its own; the API reference states the new answer.

Residual. None worth carrying.

A proxy or cache in front undoes the policy

Mechanism. A reverse proxy that answers OPTIONS itself, adds its own Access-Control-Allow-Origin: *, or a cache that ignores Vary, serves one origin's headers to another or grants what the service refused.

Likelihood and impact. Medium in real deployments, where a CORS snippet copied into nginx is common; the impact is a policy other than the configured one.

Detection. The curl check in the README, run through the proxy, shows the headers as they arrive; the example page's network panel shows a doubled header.

Mitigation. 3.3 states the rule in the operations page and in every proxy snippet; ADR-0008 and ADR-0009 assign CORS to the service.

Residual. A proxy configured against the documentation. Accepted.

The policy swap races requests

Mechanism. 2.1 replaces the policy while requests are in flight. A request that read the old pointer finishes with the old policy, which is correct; a bug in the swap could leave a nil policy for one request.

Likelihood and impact. Low with an atomic pointer that is never nil; the impact would be one request answered without CORS headers.

Detection. The lifecycle test reloads under concurrent preflights; the stress gate runs it under the race detector.

Mitigation. The disabled state is a policy value, not a nil pointer, so there is no nil to read.

Residual. None.

Header recording makes goldens brittle

Mechanism. If 0.2 recorded every response header, request ids, dates and lengths would change on every run and every transcript would move.

Likelihood and impact. Certain if done naively; the corpus would become unmaintainable.

Detection. The first regeneration.

Mitigation. Only the names a step lists are recorded, and the harness refuses X-Request-ID, Date and Content-Length in that list with a test failure that names the rule.

Residual. None.

The browser check cannot run in CI

Mechanism. Nothing in the gate opens a browser, and the project does not want a headless browser as a test dependency for one page.

Likelihood and impact. Certain; a regression that only a browser shows, such as a header name the Fetch specification treats differently from curl, would pass the gate.

Detection. The manual browser check in the release checklist, with the example page and its scripted steps.

Mitigation. The unit matrix encodes the Fetch rules that matter (wildcard tokens with credentials, echo of the specific origin, the Vary set) so that most browser-visible mistakes fail as unit tests; the scan test of 1.3 keeps the header sets in step with the handlers.

Residual. A browser-only regression between two releases. Accepted for an alpha, with the check on the list for every cut.

Parity is mistaken for a shared implementation

Mechanism. The obvious shortcut is a Go module shared by meme and TentaCron. The two APIs expose different headers and methods, meme configures from flags and TentaCron from YAML with reload, and a shared module would make both repositories release together.

Likelihood and impact. The shortcut is tempting once the code looks alike; the cost would be paid on every later change.

Detection. A review that asks why two files exist.

Mitigation. ADR-0009 records the alternative and the reason it was rejected; the test matrix shares names with meme's, so the two stay comparable without sharing code.

Residual. Two implementations to keep in step by reading, which the matrix makes cheap.
