Fix what the review found, ship it as 0.3.0-alpha

Every item below traces to a finding of the whole-repository review of 7 September. The release adds no API surface beyond what a fix needs: one configuration key for result downloads, one per-key ceiling for schedules, one error code, and a health command for the shell-less image. Everything else is a correction, a test, or a document. Every risk the plan names is answered by an item with a test of its own or by a gate in the release checklist, never by a warning alone.

Rules that apply to every item

  • One item, one conventional commit, with its tests, its documentation and its CHANGELOG.md entry under Unreleased in the same commit. Subjects are given below; bodies explain the why, as the existing history does.
  • The gate runs before every commit and must fail hard: go build ./..., go vet ./..., go test -race -shuffle=on ./..., golangci-lint run, make lint-openapi, mkdocs build --strict. Items marked timing also run the stress gate, GOMAXPROCS=2 go test -race -shuffle=on -count=3 ./....
  • Goldens change only for intended behaviour. A regenerated transcript is read line by line before it is accepted; the item text names which files are expected to move.
  • Any change to a response or an error code updates docs/openapi/openapi.yaml in the same commit; the route test, the golden validation and the Redocly lint enforce it.
  • Checkpoint after phase 1. If phase 1 took longer than three days, 0.3.0-alpha ships with the phases that are on main at that point and the rest becomes 0.3.1-alpha; every phase is a fast-forward, so a cut at any phase boundary is clean.
  • Work on a branch named after the phase (fix/phase-1-correctness, and so on), fast-forwarded onto main when the phase is green, as the earlier phases were.

OrderPhases and their dependencies

Phase 0 first, because it hardens the gate every later commit relies on. Inside phase 1, the result timeout (1.3) lands before the poll lease (1.6), which is sized by it. Inside phase 2, the testable process wiring (2.1) lands before the shutdown fix (2.2) it tests. Phase 4 is a scope decision with a rule attached: it ships only if phases 0 to 3 land inside their estimate.

Keep fake target delays far from the poll interval

Risk it answers

The poll lease (1.6) changes when ticks are claimed, and the goldens freeze call counts. A count is only a fact when the fake target's delay is nowhere near the interval; a delay close to it makes the count a race, and a race would be "fixed" by accepting whichever diff appears.

Change

Audit every poll-mode scenario in the corpus: each fake status or result delay is set either far below the scenario's poll interval or at least twice above it, and the scenario comment states which and why. A harness assertion refuses a scripted delay inside the band between half and twice the interval, so a future scenario cannot reintroduce the race.

Tests

The corpus itself, under the stress gate three times; no golden may change in this commit.

Rescue stuck jobs by their target's own attempt deadline

Problem

The sweeper requeues any job in resolving or forwarding untouched for twice worker.job_timeout, but a target may set a longer job_timeout, validation does not bound it, and nothing refreshes updated_at during an attempt. A legitimate 11-minute simulation under the 5-minute default is requeued and forwarded again by a second worker while the first still runs, and the two then race the state machine.

Change

RescueStuck takes a cutoff function per target instead of one time: it selects the in-flight rows with their target and timestamp (there are never many) and rescues those older than twice that target's deadline, JobTimeoutFor(target). A job whose target vanished from the configuration falls back to the worker default. No heartbeat, no schema change.

Tests
  • Store: two in-flight jobs untouched for 12 minutes, one on a target with a 20-minute deadline, one on the default; only the second is rescued.
  • Worker: the sweeper runs with a fake target that answers after the worker default has passed; the job completes once and the target received exactly one forward.
  • Stress gate.
Docs

Operations, Housekeeping and Failure handling: "twice the target's attempt deadline". Architecture, Restart safety. CHANGELOG under Fixed.

fix(worker): rescue stuck jobs by their target's own attempt deadline

Bound a result download by its own result_timeout

Problem

The whole result stream runs under the target's per-call timeout, 60 seconds by default, and under the job timeout on top. A bundle anywhere near the 1 GiB cap cannot finish; the failure classifies as transient and the tick retries until the poll deadline ends the job as target_error, although the target's work succeeded.

Change

New key response.poll.result_timeout, default 10 minutes, validated to be at least timeout. Two bounds on the stream, because they answer different failures: an idle bound equal to timeout, renewed after every read, so a stalled connection fails as fast as any other call; and result_timeout as the total, so a slow but moving download of a large bundle is allowed to finish. The status call keeps timeout. A poll tick no longer runs under the job's attempt deadline, which was written for resolution and forwarding: the download context derives from the bookkeeping context. The transport gets a ResponseHeaderTimeout equal to timeout.

Tests
  • Config: default applied, a value below timeout refused, the example configs still validate.
  • Upstream: a stream that stalls for longer than timeout fails within it; one that keeps moving past timeout succeeds; one that outlasts result_timeout ends as a transient error.
  • Worker: a download that outlasts the call timeout completes the job; result_calls is one.
Docs

Configuration, targets table. Operations, Result sizes. Both reference configs gain the key on the meme target with a comment. CHANGELOG under Added (the key) and Fixed (the behaviour).

Skip clients at their ceiling when choosing claim candidates

Problem

claimCandidates takes eight rows ordered by priority first. A client at its max_concurrent ceiling whose jobs outrank the others fills the batch, every candidate is skipped, and the worker reports no work while other clients' jobs are due.

Change

Lease a poll tick for its whole duration

Problem

A tick is claimed by pushing next_attempt_at forward by the poll interval only. A tick that outlasts the interval, a result download for instance, is claimed again by another worker; the duplicate completion is dropped safely, but the download runs twice.

Change

The claim leases the tick for timeout + result_timeout + interval. When a tick ends with the job still waiting, the worker reschedules explicitly to now + interval with a compare-and-set on the state; the reschedule runs in a defer, so every way out of a tick, including a recovered panic, restores the cadence. A worker that dies mid-tick is covered by the lease expiring. Startup recovery resets the next poll of every waiting job to a point spread at random across one interval, so a long lease never delays the first poll after a restart and a restart never sends every waiting job's status call in the same instant.

Tests
  • Store: a leased tick is not claimable before the lease ends; the reschedule fails once the job left awaiting_target.
  • Worker: a status endpoint slower than the interval is polled once per tick, not twice; a restart polls within one interval. Written before the change on the fakes 0.4 made deterministic, and seen failing on the old code.
  • Worker: a tick that panics still reschedules; a tick that ends the job does not.
  • Goldens that count polls may move: result-fetch-flaky-then-success, awaiting-target-mid-flight, the two target-timeout transcripts. Expected direction is fewer duplicate calls; anything else is a regression.
  • Stress gate.
Docs

Architecture, Queue semantics and Restart safety. CHANGELOG under Fixed. The follow-up note in the project notes is closed.

fix(worker): lease a poll tick for its whole duration

End long-polls at shutdown and let a second signal force exit

Problem

A long-poll waits up to write_timeout minus five seconds, 25 by default, the grace window is 20, and http.Server.Shutdown does not cancel request contexts, so a drain overruns and logs an incomplete shutdown. A second interrupt during a hung shutdown does nothing, because the signal context is only released after serve returns.

Change

The server exposes a draining channel closed when the drain begins, and only the long-poll wait selects on it, answering with the current state at once. Request contexts are deliberately not cancelled: that would abort in-flight writes and turn a graceful shutdown into 500s for clients mid-request. The signal context is released as soon as the first signal arrives, so a second one terminates the process with Go's default behaviour. Target-cancel notifications are tracked in a wait group the drain waits for, bounded by the target timeout.

Tests

The lifecycle test asserts a long-poll opened before shutdown returns 200 within a second of the signal. An API test asserts awaitTerminal returns when the draining channel closes, and that a request in flight during the drain completes normally.

Docs

Operations, Failure handling row Shutdown, and a sentence on the second signal. CHANGELOG under Fixed.

Keep delivering after a reload and fail what the allow-list no longer covers

Problem

When a reload empties callbacks.allowed_hosts, the deliverer stops entirely and every pending delivery stays pending forever, visible as such in the API.

Change

The loop runs whenever deliveries are due. Each attempt re-checks the URL against the current allow-list: a URL that still passes is delivered; one that no longer passes counts as a failed attempt with the reason in last_error and follows the backoff like any other, so a mistaken reload is reversible and the delivery is given up only when the attempt budget runs out. The API shows the reason meanwhile.

Tests

Deliverer: a pending delivery is delivered after callbacks were re-enabled; one whose host was removed stays pending with the reason, is delivered once the host is restored, and fails only when the budget runs out.

Attest build provenance for binaries and the image

Problem

The release publishes checksums but nothing that ties them to the workflow that built them.

Precondition

Artifact attestations are available for public repositories, so this item waits until the repository is public. If it is not public by the release, the item moves to 0.4.0 unchanged and the release notes say so.

Change

Proven before it is promised: the CI build job first attests the binary it already compiles, guarded to pushes and same-repository pull requests because a fork's run has no identity token and would fail every outside contribution otherwise; a missing permission then fails a branch rather than a tag. Then the same step, actions/attest-build-provenance with the id-token and attestations permissions, attests the release binaries and the image digest. The image attestation takes the digest from the build step and pushes to the registry alongside the tags. Operations gains both verification forms, the binary with --owner enerplanet and the image by digest, and SECURITY.md lists provenance among what is in place. Needs no secrets.

Tests

The branch attestation, then the pre-release run; the verification command in the docs is executed against the pre-release before the docs claim it works.

Cap a key's queued requests with max_queued

Problem

A client may enqueue without limit, a hundred per batch call; max_concurrent limits processing, not the queue. The database grows until retention, and one runaway client shapes everyone's latency.

Change

auth.api_keys[].max_queued, default 0 meaning unlimited: the count of the client's non-terminal requests. Above it, submission answers 429 queue_full with Retry-After set to the worker poll interval; batch items are refused individually with the same code. The count runs inside the insert transaction like the schedule cap, over a new index on (client, state) so it costs one range scan rather than a table walk under load.

Tests

Store: atomic under concurrent submits. New golden queue-full for the single and the batch path. OpenAPI: the code, the 429 with its header, an example.

API reference, Configuration auth table, Operations alert suggestion. CHANGELOG under Added.

The poll lease moves golden call counts

Mechanism. The corpus polls every 10 ms with a 2 s poll timeout, and the fakes answer in microseconds, so no tick outlasts the interval there today and none will after the lease. Ten transcripts freeze poll counts; the only way the lease can move one is the explicit reschedule at the end of a tick: a path that ends a tick without it leaves the job leased for timeout + result_timeout + interval, seconds in the corpus, minutes in production. In the corpus that shows up as an await timeout, a hard failure, never a quietly changed count.

Likelihood and impact. Low. Missed, the failure mode changes from duplicated work, today's behaviour, to a delayed poll, which is worse for one job and better for the target.

Detection. The band assertion from 0.4, the lease test written first, the corpus under the stress gate, and the panic-path test.

Mitigation. The reschedule runs in a defer (1.6), so every exit restores the cadence; a restart spreads the reset polls across one interval instead of firing them together.

Residual. A worker killed mid-tick delays that job's next poll until the lease expires or the process restarts. Accepted and documented; the metric for it, a gauge of leased ticks, is a 0.4.0 idea.

The ceiling-aware claim costs a query per claim

Mechanism. The added count reads only rows in resolving or forwarding through the state index. Those are the claimed jobs: at most one per worker plus any stuck ones, so the query is proportional to the worker count, not to the queue. The expensive part of a claim is older: the window function ranks every due job to pick eight, which is n log n in the backlog. A backlog stays small unless a target is down for hours and retries pile up.

Likelihood and impact. A regression from 1.5 is very unlikely. The pre-existing cost is real but only under a backlog of tens of thousands, where each claim would take milliseconds; not a cliff at the service's stated scale.

Detection. The benchmark in 1.5, with and without a ceiling, ten thousand queued jobs, before and after.

Mitigation. The count is skipped when no key configures a ceiling; the benchmark stays in the package.

Residual. The ranking cost. If the benchmark makes it matter, 0.4.0 picks each client's head with a per-client subquery instead of ranking all due rows.

New error codes reach the API undocumented

Mechanism. Codes live in three places: the API constants, the plan's dry-run codes, and the worker's private strings, some of which alias the plan's. The description has three enums: the API error, the job error and the dry-run problem. The golden validation only sees codes a transcript records; a code no scenario exercises can be undocumented and still ship.

Likelihood and impact. Moderate without the test, since two items add codes. The impact is a client generated from the description that rejects a real response.

Detection. The parity test from 0.5, both directions, and the literal-scan test beside it.

Mitigation. One exported list per family; the worker's aliases removed; the test maps families to enums.

Residual. None worth naming: a code can only be a constant, and every constant is in the description.

Attestations fail on the tag

Mechanism. Attestations need a public repository on this plan, the id-token and attestations permissions, and for the image the registry push permission. A run triggered by a fork's pull request has no identity token at all, so an unguarded attest step would fail every outside contribution once the repository is public.

Likelihood and impact. High without the guard, because contributors arrive with publicity. The impact of a failing release run is a red tag and a manual retry, not a broken artifact.

Detection. The branch attestation in CI, before the release workflow changes.

Mitigation. The guard and the precondition in 3.1; the verification commands executed against the pre-release before the docs claim them.

Residual. None once verified.

Migrations meet a live database

Mechanism. 0008 builds an index over every job at startup inside one transaction, seconds at current volumes, during which readiness waits. 0009 adds a nullable column and a partial unique index. Both are additive. Rollback is therefore possible: the previous binary ignores migration versions it does not know and never selects the new column, so a 0.2.0-alpha binary opens a 0.3.0-alpha database. The trap is elsewhere: tentacron backup migrates the database it opens, so the documented "back up before upgrading" run with the new binary migrates first and backs up second.

Likelihood and impact. The trap is certain for anyone following the docs with the new binary. Its impact is a backup that is no longer of the old schema, which defeats the reason for taking it.

Detection. The backup test in 2.11 fails on today's code.

Mitigation. 2.11 opens read-only and refuses a newer schema; 2.10 rehearses the upgrade over a populated database and states that rollback works; the readiness checklist rehearses it once more against a real copy.

Residual. A rollback across more than one release is not covered and is not promised.

The alpha meets real endpoints only in production

Mechanism. Every test speaks to fakes: no TLS, no latency, no bundles of real size, no real 429. The changed paths are the meme poll and result download (1.3, 1.6) and long synchronous targets (1.1). Callbacks need an https receiver on an allow-listed host, which the live tier does not provide.

Likelihood and impact. A timing constant tuned on fakes is the classic escape; the impact is a job that fails or stalls against the one target that matters.

Detection. The live tier against staging through meme and buem, transcript attached to the release pull request.

Mitigation. A line in the readiness checklist that blocks the tag.

Residual. Cancellation and callbacks are proven by the goldens only. A staging callback receiver is a small 0.4.0 task.
